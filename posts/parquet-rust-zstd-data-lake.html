Modern Data Lake Essentials: Boosting Storage and Query Performance with Parquet, Rust, and ZSTD

Date: August 19, 2026 • Author: Alex

When building a modern data platform, choosing the right file format and compression strategy can make or break your infrastructure. If you are still relying on text-based formats like CSV or JSON for analytical workloads, you are burning money on storage and wasting precious CPU cycles.

In this benchmark and architectural guide, we explore why Apache Parquet coupled with ZSTD compression is the gold standard for modern data lakes, how to read and write these files with blazing-fast Rust, and how to query and lifecycle-manage them at cloud scale.

1. Why Parquet and ZSTD Savage CSV/JSON in Storage

Analytical datasets are vast. In our benchmark, a standard raw dataset that takes 16 GB in CSV or JSON shrinks to just 3.2 GB in Parquet + ZSTD—a staggering 5x reduction in storage footprint.

Format & Compression Storage Benchmark (100M Rows Dataset):
File Format Compression File Size Scan Time (1 Col) Compression Ratio
Raw JSON None 18.4 GB 12.4s 1.0x (Baseline)
Uncompressed CSV None 16.0 GB 9.8s 1.15x
Parquet Snappy 4.1 GB 0.6s 4.5x
Parquet ZSTD (Level 3) 3.2 GB 0.4s 5.75x

Parquet achieves this through three core design concepts:

  • Columnar Layout: Stores columns contiguously. Analytical queries selecting specific columns skip full-row scans entirely.
  • Intelligent Encoding: Uses Dictionary, RLE, and Bit-Packing encoding to replace repetitive data with compact representation.
  • ZSTD (Zstandard) Codec: Offers Gzip-like compression ratios while maintaining Snappy-level decompression speeds.

2. Implementing Parquet & ZSTD in Rust

Rust has become a powerhouse for modern data engineering infrastructure. Below are the two standard approaches to read and write Parquet files with ZSTD compression in Rust.

Approach A: High-Level DataFrames using Polars

Add to Cargo.toml:

[dependencies] polars = { version = "0.45", features = ["parquet", "fmt"] }

Implementation Example:

use polars::prelude::*;
use std::fs::File;

fn main() -> Result<(), PolarsError> {
    // 1. Build sample columns
    let id_col = Column::new("id".into(), &[1, 2, 3]);
    let name_col = Column::new("name".into(), &["Alice", "Bob", "Charlie"]);
    let age_col = Column::new("age".into(), &[28, 34, 45]);

    // 2. Instantiate DataFrame
    let df = DataFrame::new(vec![id_col, name_col, age_col])?;

    // 3. Write with ZSTD compression
    let write_file = File::create("users_zstd.parquet")?;
    ParquetWriter::new(write_file)
        .with_compression(ParquetCompression::Zstd(None))
        .finish(&df)?;

    // 4. Read back
    let read_file = File::open("users_zstd.parquet")?;
    let loaded_df = ParquetReader::new(read_file).finish()?;
    println!("Loaded DataFrame:\n{}", loaded_df);

    Ok(())
}

Approach B: Low-Level Memory Control via Apache Arrow/Parquet

Add to Cargo.toml:

[dependencies] arrow = { version = "53" } parquet = { version = "53", features = ["zstd"] } 
use arrow::array::{Int64Array, StringArray};
use arrow::record_batch::RecordBatch;
use parquet::arrow::ArrowWriter;
use parquet::basic::Compression;
use parquet::file::properties::WriterProperties;
use std::fs::File;
use std::sync::Arc;

fn main() {
    let schema = Arc::new(arrow::datatypes::Schema::new(vec![
        arrow::datatypes::Field::new("id", arrow::datatypes::DataType::Int64, false),
        arrow::datatypes::Field::new("name", arrow::datatypes::DataType::Utf8, false),
    ]));

    let id_array = Int64Array::from(vec![1, 2, 3]);
    let name_array = StringArray::from(vec!["Alice", "Bob", "Charlie"]);

    let batch = RecordBatch::try_new(
        schema.clone(),
        vec![Arc::new(id_array), Arc::new(name_array)]
    ).unwrap();

    let props = WriterProperties::builder()
        .set_compression(Compression::ZSTD(None))
        .build();

    let file = File::create("arrow_zstd.parquet").unwrap();
    let mut writer = ArrowWriter::try_new(file, schema, Some(props)).unwrap();
    writer.write(&batch).unwrap();
    writer.close().unwrap();

    println!("Successfully flushed Arrow ZSTD Parquet file to disk!");
}

3. Querying at Scale: Athena vs. Apache Spark

When executing queries across millions of Parquet files in S3/Object Storage, engine choice determines both execution speed and cloud cost.

AWS Athena (Serverless Presto/Trino)

  • • Cost Model: Billed per TB scanned ($5.00/TB).
  • • ZSTD Advantage: Smaller file size directly translates to linear cost savings per SQL query.
  • • Best Use Case: Ad-hoc analytical queries, reporting, and low-frequency dashboards.

Apache Spark / EMR

  • • Cost Model: Billed per compute node instance hour.
  • • ZSTD Advantage: Fast decompression reduces executor CPU waiting times and worker node RAM consumption.
  • • Best Use Case: Large-scale ETL/ELT pipelines, streaming processing, and batch ML feature engineering.

4. Automating Lifecycle Costs with AWS S3

Combining efficient Parquet + ZSTD formatting with S3 Lifecycle policies ensures long-term retention cost optimization. As analytical data ages from active query layers to compliance archives, automated transitions dramatically reduce TCO.

Recommended Data Lifecycle Architecture:
Age Horizon Storage Tier Format Policy Cost / GB / Month
0 - 30 Days S3 Standard Parquet + ZSTD (Hot) $0.023
30 - 90 Days S3 Standard-IA Parquet + ZSTD (Warm) $0.0125
90 - 365 Days S3 Glacier Flexible Parquet + ZSTD (Cold Archive) $0.0036
> 365 Days S3 Glacier Deep Archive Parquet + ZSTD (Compliance) $0.00099

5. Architectural Recommendation

For modern cloud data platforms, adopting **Parquet + ZSTD** in combination with **Rust microservices** for ingestion and **S3 Lifecycle rules** offers maximum performance at minimal cost:

  1. Ingestion Layer: Use Rust (`polars` or `parquet` crate) to convert streaming logs or raw JSON payloads into compressed Parquet files.
  2. Storage Layer: Store data in S3 partitioned by date (`year=YYYY/month=MM/day=DD`) with ZSTD compression level 3.
  3. Query Layer: Route ad-hoc queries to Athena while running heavy batch operations via Spark/EKS or native Rust DataFusion nodes.
